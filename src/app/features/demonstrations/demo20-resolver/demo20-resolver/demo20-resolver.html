Resolver

Qu'est-ce qu'un resolver ?

Un resolver permet de récupérer des données avant le chargement du composant. Le routeur exécute le resolver, attend le résultat, puis active le composant : celui-ci démarre avec ses données déjà prêtes.

Sans resolver, le flux habituel est inversé : le composant s'affiche d'abord (vide), lance son appel HTTP dans ngOnInit, puis se remplit à l'arrivée de la réponse — d'où un « flash » de contenu vide et des @if de garde un peu partout dans le template.

Avec ou sans resolver ?

  • Sans resolver : clic → navigation immédiate → composant vide → chargement → affichage. L'utilisateur voit un état intermédiaire ;
  • Avec resolver : clic → chargement des données → navigation → composant complet dès le premier rendu. L'utilisateur reste sur la page précédente pendant le chargement.

Créer un resolver

Un resolver moderne est une simple fonction typée ResolveFn<T>. On y accède aux services via inject(), comme dans un guard fonctionnel :

// car.resolver.ts
import { ResolveFn, Router } from '@angular/router';
import { inject } from '@angular/core';
import { Car } from '../../features/car-features/car.model';
import { CarService } from '../services/car/car-service';

export const carResolver: ResolveFn<Car | null> = (route, state) => {

  const carService = inject(CarService)
  const id = route.paramMap.get('id')
  const router = inject(Router)

  // Pas d'id dans l'URL : rien à charger
  if(!id){
    return null;
  }

  const car : Car | undefined = carService.getCarById(parseInt(id))

  // Voiture introuvable : on redirige et on abandonne
  if(car === undefined){
    router.navigateByUrl('')
    return null;
  }

  return car;
};

La fonction peut retourner une valeur synchrone (comme ici, le service travaillant en mémoire), un Observable ou une Promise. Les appels HttpClient conviennent parfaitement : ils émettent leur réponse puis complètent aussitôt.

Déclarer le resolver sur la route

On l'attache à la route via la propriété resolve, un objet clé / resolver :

// app.routes.ts
export const routes: Routes = [
    {
        path: 'cars/:id',
        component: CarDetailComponent,
        resolve: { car: carResolver }
    }
];

La clé choisie (car) n'est pas anodine : c'est sous ce nom que la donnée résolue sera exposée au composant.

Récupérer la donnée dans le composant

Approche moderne (Angular 16+) : activer le binding des données de route vers les inputs dans la configuration du routeur...

// app.config.ts
provideRouter(routes, withComponentInputBinding())

...la donnée arrive alors directement dans un input signal portant le même nom que la clé du resolve :

export class CarDetailComponent {
    // Reçoit automatiquement la valeur résolue sous la clé 'car'
    car = input.required<Car | null>();
}

Alternative classique via ActivatedRoute :

export class CarDetailComponent {
    private route = inject(ActivatedRoute);

    car = this.route.snapshot.data['car'] as Car | null;
}

Le type suit celui du resolver (Car | null) : un @if (car()) dans le template couvre le cas absent.

Gérer les erreurs

Si un resolver échoue sans rien prévoir, la navigation est annulée silencieusement : l'utilisateur reste sur la page précédente, sans aucun message. Dans notre resolver synchrone, le cas est déjà couvert : voiture introuvable → router.navigateByUrl('') puis return null.

Le jour où CarService passera sur HttpClient, le même réflexe s'écrit avec catchError :

export const carResolver: ResolveFn<Car | null> = (route) => {
    const router = inject(Router);

    return inject(CarService)
        .getCarById(Number(route.paramMap.get('id')))
        .pipe(
            catchError(() => {
                router.navigateByUrl('');
                return EMPTY; // complète sans émettre : navigation abandonnée proprement
            })
        );
};

Limites et bonnes pratiques

  • La navigation est bloquée pendant le chargement : sur un appel lent, le clic semble ne rien faire. Prévoir un indicateur global en écoutant les événements du routeur (NavigationStart / NavigationEnd) ;
  • À réserver aux données indispensables au premier rendu ; pour du contenu secondaire, un chargement classique dans le composant reste préférable ;
  • L'Observable retourné doit compléter : un BehaviorSubject exposé tel quel bloque la navigation indéfiniment (le limiter avec take(1) si besoin) ;
  • Le resolver est ré-exécuté à chaque changement de paramètre de la route (navigation de /cars/1 vers /cars/2) ;
  • On centralise la récupération des données dans le resolver et le service : le composant reste simple, sans logique de chargement, et donc testable.
