LocalStorage & SessionStorage

Le navigateur offre deux espaces de stockage clé / valeur permettant de conserver des données côté client, sans base de données ni serveur : le localStorage et le sessionStorage.

Ce sont des API du navigateur (Web Storage API), pas des fonctionnalités Angular — elles s'utilisent donc de la même façon dans n'importe quelle application web.

Quelle différence entre les deux ?

Les deux ont exactement la même API. Seule leur durée de vie change :

  • localStorage : les données persistent — fermeture du navigateur, redémarrage du PC... elles restent jusqu'à suppression explicite (par le code ou par l'utilisateur qui vide ses données de navigation) ;
  • sessionStorage : les données vivent le temps de l'onglet — fermer l'onglet les efface, et chaque onglet possède son propre stockage, même sur le même site.

Cas d'usage typiques : préférences utilisateur, thème, panier, brouillon de formulaire pour localStorage ; état temporaire d'un parcours (étape d'un wizard, filtre en cours) pour sessionStorage.

L'API

Quatre méthodes principales, identiques pour les deux :

// Écrire (clé, valeur)
localStorage.setItem('theme', 'dark');

// Lire — retourne null si la clé n'existe pas
const theme = localStorage.getItem('theme');

// Supprimer une clé
localStorage.removeItem('theme');

// Tout vider
localStorage.clear();

⚠️ Le storage ne stocke que des chaînes de caractères. Pour un objet ou un tableau, il faut sérialiser en JSON à l'écriture et désérialiser à la lecture :

// Écriture d'un objet
const user = { name: 'Zac', theme: 'dark' };
localStorage.setItem('user', JSON.stringify(user));

// Lecture — attention au null si la clé n'existe pas
const raw = localStorage.getItem('user');
const savedUser = raw ? JSON.parse(raw) : null;

Bonnes pratiques dans Angular

Plutôt que d'appeler localStorage directement dans les composants, on centralise les accès dans un service : une seule source de vérité, la sérialisation JSON gérée à un seul endroit, et des composants qui restent testables.

Combiné aux signaux, le pattern classique est : un signal comme état réactif, et un effect qui sauvegarde automatiquement à chaque changement :

@Injectable({ providedIn: 'root' })
export class ThemeService {
    theme = signal<string>(localStorage.getItem('theme') ?? 'light');

    constructor() {
        // À chaque changement du signal, on persiste
        effect(() => {
            localStorage.setItem('theme', this.theme());
        });
    }
}

Le composant ne parle qu'au signal — la persistance est invisible pour lui.

Limites et sécurité

  • Capacité limitée à environ 5 Mo par origine (domaine) ;
  • Stockage synchrone : à réserver aux petites données (pour du volume, il existe IndexedDB) ;
  • Le stockage est isolé par origine : un autre site ne peut pas lire vos données ;
  • Mais tout script s'exécutant sur votre page y a accès (risque XSS) : on n'y stocke jamais de données sensibles — mots de passe, données personnelles critiques.
